\chapter{Methodology}\label{chap:Methodology}

This chapter describes the methodology used to design and implement TaskFlow.
It begins with a structured requirements analysis and a high-level system
architecture overview, then examines each major subsystem through the lens of
design decisions, architectural trade-offs, and alternative approaches considered.
The chapter closes with a discussion of the testing strategy applied throughout
development.

\section{Requirements Analysis}\label{sec:meth_requirements}
% ─────────────────────────────────────────────────────────────────────────────

\subsection*{Functional Requirements}

The following functional requirements were identified from the project objectives stated
in Section~\ref{sec:intro_aims}:

\begin{enumerate}
    \item \textbf{FR-01 User Authentication.}
          The system shall support user registration, login, and password reset.
          Credentials shall be stored using a salted, one-way hash and protected
          against replay attacks.

    \item \textbf{FR-02 Task Management.}
          Users shall be able to create, read, update, and delete tasks.
          Each task shall carry a title, optional description, configurable priority,
          status, optional due date, star flag, and project assignment.

    \item \textbf{FR-03 Multiple Task Views.}
          Tasks shall be displayable in five views: a smart-grouped default list, a
          Kanban board, a tabular grid, a Gantt timeline, and a calendar time-grid.

    \item \textbf{FR-04 Project and Team Management.}
          Users shall be able to create projects, invite team members, and assign tasks
          to projects. Invitations shall be delivered across devices.

    \item \textbf{FR-05 Messaging.}
          Users shall be able to exchange one-to-one direct messages and participate in
          group chats, both with optional file attachments.

    \item \textbf{FR-06 Notifications and Reminders.}
          The system shall deliver real-time in-application notifications and optional
          email reminders at user-configured times.
          Automated warnings shall fire before task due dates.

    \item \textbf{FR-07 Calendar Events.}
          Users shall be able to create, edit, and delete calendar events with temporal
          boundaries, an optional colour, and an optional meeting link.

    \item \textbf{FR-08 AI Chatbot.}
          A conversational AI assistant shall be available in three modes: general
          conversation, code generation, and document scanning.
          Responses shall be delivered token-by-token as they are generated.
          Conversation history shall be persisted between sessions.

    \item \textbf{FR-09 Offline Operation.}
          All core task-management features shall function without network access.
          Locally generated changes shall be queued and synchronised when connectivity
          is restored.

    \item \textbf{FR-10 Dashboard.}
          A dashboard shall display summary statistics, a task-trend indicator, tasks
          due within the current week, a recent-activity feed, and an embedded calendar
          widget.

    \item \textbf{FR-11 Settings.}
          Users shall be able to update their profile, change their password, and manage
          notification preferences.
\end{enumerate}

\subsection*{Non-Functional Requirements}

\begin{enumerate}
    \item \textbf{NFR-01 Offline Availability.}
          The application shall start and remain fully operable without network access.

    \item \textbf{NFR-02 Security.}
          All API endpoints shall require authentication. Passwords shall not be stored
          in recoverable form. The application shall be resistant to common web
          vulnerabilities including SQL injection.

    \item \textbf{NFR-03 Cross-Platform Distribution.}
          The packaged installer shall run on Windows, macOS, and Linux without
          requiring the user to install any additional runtime.

    \item \textbf{NFR-04 Responsiveness.}
          UI interactions shall produce visible feedback within 200~ms under normal
          conditions.

    \item \textbf{NFR-05 Extensibility.}
          The backend shall be structured so that new entity types can be added without
          modifying existing controller logic.
\end{enumerate}

\section{System Architecture Overview}\label{sec:meth_arch}
% ─────────────────────────────────────────────────────────────────────────────

TaskFlow is structured as a three-tier desktop application embedded in a native
operating-system shell.

\textbf{Tier 1 --- Presentation Layer.}
The user interface is a single-page application built with React and TypeScript.
It communicates with the backend exclusively through HTTP REST calls and a
persistent WebSocket connection for real-time events. The choice of an SPA
architecture over server-side rendering was motivated by the need for a
responsive, application-like feel in a desktop context, where page reloads would
disrupt the user experience.

\textbf{Tier 2 --- Application Logic Layer.}
The backend exposes a REST API and a real-time event hub. It follows a layered
architecture: HTTP controllers delegate to service classes, which in turn use
data-access objects for persistence. A mapping layer projects internal entity
models onto response objects at the service boundary, preventing internal
representation details from leaking into the API surface. A global error-handling
mechanism catches unhandled exceptions and returns a uniform error response,
ensuring that no internal state or stack trace is ever exposed to the client.
This layered structure was chosen to maintain separation of concerns and to
allow individual layers to be tested or replaced independently.

\textbf{Tier 3 --- Data Layer.}
Two database systems are employed for different purposes. A local embedded
database serves as the primary, always-available store that operates without any
network dependency. A cloud document database acts as an optional relay used
exclusively for cross-device synchronisation and team collaboration features.
The application starts and runs normally even when the cloud database is
unreachable. This dual-store design was adopted to satisfy the offline-availability
requirement (NFR-01) while still enabling multi-device and team workflows.

\textbf{Desktop Shell.}
A lightweight native shell launches the compiled backend as a managed child
process. It monitors the child's output for a readiness signal before revealing
the application window, ensuring that the user interface is never shown before
the API is ready to serve requests. Using a native shell rather than bundling a
full browser engine reduces the application's disk and memory footprint, as it
leverages the operating system's built-in webview component.

\textbf{Request Lifecycle.}
A typical authenticated request flows through the layers in sequence: the
React component issues an HTTP request with the user's identity --- the
shell process adds the authenticated user's email to every outgoing request.
The backend middleware resolves this identity into a principal object that is
carried through the remainder of the request pipeline. The controller delegates
to a service, which performs the business logic and persists changes through the
data-access layer. If the operation mutates a synchronisable entity, the service
additionally triggers the synchronisation engine, which either applies the change
directly to the cloud database (if online) or enqueues it for later replay (if
offline). Real-time events are broadcast to the connected client via the
persistent WebSocket connection independently of the HTTP response path.

\section{Data Layer Design}\label{sec:meth_data}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Dual-Store Strategy}

The central design decision in the data layer was the adoption of two distinct
database systems serving complementary roles. A local embedded database
(SQLite) provides the primary persistence layer with zero network dependency,
satisfying the offline-availability requirement. A cloud document database
(MongoDB) acts as a synchronisation relay for cross-device features: team
invitations, membership rosters, presence information, and mirrors of
synchronisable entities such as tasks and notifications.

This dual-store approach introduces inherent complexity --- every write to a
synchronisable entity must eventually be reflected in both stores, and the
system must handle periods where only one store is reachable. An alternative
considered was a cloud-only architecture with a local cache, but this was
rejected because it would make the application unusable during network
outages, violating NFR-01. Conversely, a local-only architecture would prevent
multi-device and team features entirely. The chosen design occupies a middle
ground: the cloud store (MongoDB) is authoritative, and the local store is a
local cache whose consistency with the source of truth is maintained by an
outbox-based synchronisation engine.

\subsection{Synchronisation Model}

Entities that must be replicated to the cloud store are identified at design
time. Each such entity carries a globally unique identifier assigned at
creation time, which serves as the document key in the cloud database. This
design enables idempotent operations: replaying the same synchronisation entry
twice produces the same document rather than a duplicate. A timestamp field
records the most recent modification and serves as the arbitration key in a
last-write-wins conflict-resolution strategy, which was chosen for its
simplicity and because concurrent edits to the same entity across different
devices are expected to be rare in a personal-task-management context.

A dirty flag on each synchronisable entity indicates whether the local record
has been propagated to the cloud. The persistence layer automatically stamps
the modification timestamp and resets the dirty flag on any tracked change,
eliminating the need for manual bookkeeping in service code.

\subsection{Entity Model}

The application manages eighteen entity types in the local database, grouped
into identity, work items, team and social structures, messaging, time-related
records, alerts, AI conversation history, and synchronisation metadata. Unique
indexes on the global identifiers of synchronisable types prevent duplicate
inserts if the application is restarted during a synchronisation pass.
Entity types that are read-only mirrors of cloud documents --- such as
team memberships and invitations pulled on login --- use the cloud document
identifier as their local primary key.

\subsection{MongoDB Collection Design}

Five collections are maintained in the cloud database:

\begin{itemize}
    \item Synchronisation mirrors of the primary work entities (tasks,
          notifications), keyed by their global identifiers.
    \item A team-invitations collection indexed by recipient email and status,
          enabling pending invitations to be delivered to any device the
          recipient logs into.
    \item A team-membership collection indexed by team and owner, serving as
          the roster for team-wide features.
    \item A user-presence collection for online-status indication across
          devices.
\end{itemize}

This minimal cloud schema reflects the design principle that the cloud store
exists solely to enable cross-device and team collaboration --- it is not a
backup or primary store.

\section{Backend Design}\label{sec:meth_backend}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Authentication Service}\label{sec:meth_auth}

User registration follows a three-step process: input validation, credential
hashing, and persistence. The choice of a salted, adaptive hash function
(bcrypt) for password storage was made to resist brute-force attacks even if
the local database file is compromised --- a realistic threat model for a
desktop application whose data resides on the local filesystem.

Login validates the submitted password against the stored hash and, on success,
returns the user's identity profile. No token is issued; the session is managed
by middleware that reads the authenticated user's email from each request header
and resolves the corresponding identity from the local database. This approach
was chosen over a token-based scheme --- such as JWT --- to eliminate token
issuance, refresh, and revocation complexity in a single-user desktop context
where the HTTP client and server are always on the same machine and the
identity header is set by the trusted native shell rather than by an external
browser. A post-login synchronisation step immediately refreshes local copies of
team memberships and pending invitations from the cloud database.

Password reset uses a locally generated recovery code that is written to a
temporary file on the filesystem and read by the native shell through an
inter-process communication bridge. The reset code is time-limited,
and the reset endpoint validates the code, checks expiry, and updates the
password hash in both the local and cloud databases.

\subsection{Task and Project Management}\label{sec:meth_tasks}

The task entity is the central data structure of the system, carrying metadata
such as priority (three levels), status (five states), and project association.
The status model includes both user-set states and an automatically assigned
overdue state computed by a background process that monitors approaching due
dates.

All mutating operations enforce ownership by comparing the authenticated
user's identity against the owner field of the target entity, rejecting
unauthorised access attempts with an appropriate error response. Text search is
executed at the database layer rather than in application memory, ensuring that
search performance degrades gracefully as the dataset grows.

After any create or update operation on a synchronisable entity, the service
triggers the synchronisation engine. The engine checks the current
connectivity state: if online, it applies the change to the cloud database
directly; if offline, it serialises the change as an outbox entry in the local
database for later replay.

\subsection{Real-Time Notification System}\label{sec:meth_notifications}

The notification subsystem provides real-time delivery of alerts --- task due
date warnings, reminder firings, and team-related events --- without requiring
the client to poll. The system uses a persistent WebSocket connection
established at application startup. Each client is assigned to a user-specific
channel upon connection, allowing the backend to address notifications to
individual users efficiently.

A hierarchy of notification types across several priority levels is defined,
each carrying contextual information that allows the frontend to navigate the
user to the relevant resource when the notification is clicked. Two background
processes supplement the push-based hub: one monitors approaching task due
dates and fires both in-app notifications and (if configured) email alerts,
using an in-memory deduplication mechanism to avoid repeated warnings for the
same task within a session; the other fires user-configured reminders whose
scheduled time has passed.

\subsection{Messaging System}\label{sec:meth_messages}

The messaging module provides two conversation types. Direct messages store a
sender, a receiver, a text body, a read flag, and separate soft-delete flags
for each party. This design ensures that a message deleted by one party remains
visible to the other until they also delete it --- a pattern favoured by
privacy-conscious messaging applications. The system enforces a configurable
attachment size limit at the HTTP server level.

Group chats store a name, description, and owner, with a join entity linking
participants to the group. Group messages extend the attachment model of direct
messages with an edit-tracking flag. After persisting each message, the backend
broadcasts a real-time event to the recipient's notification channel (for
direct messages) or to a channel scoped to the group, enabling real-time
delivery without polling.

\subsection{Offline Synchronisation Engine}\label{sec:meth_sync}

The synchronisation subsystem comprises three cooperating components that
together implement the outbox pattern.

A connectivity-monitoring component maintains the effective connectivity state
of the application by periodically probing the cloud database. It exposes the
current state --- online, manually-offline, or disconnected --- and the count
of pending synchronisation entries, and emits events when the state changes.
A user-toggled manual-offline mode is provided to allow explicit control over
when synchronisation occurs, which is particularly useful during testing.

A background synchronisation worker replays the outbox. It runs a periodic
probe loop that updates the connectivity state. When the state transitions from
offline to online, it waits briefly for the connection to stabilise and then
processes each pending outbox entry sequentially: each entry is advanced through
Pending, Processing, Synced, or Failed states, with failed entries recording an
attempt count and error information for diagnostic purposes. Throughout the
replay process, progress events are broadcast to the client via the real-time
notification channel, allowing the frontend to display an animated progress
indicator.

A startup synchronisation service runs once at application launch. It waits for
the cloud database to become reachable for a configurable period, then performs
a bulk reconciliation of all synchronisable entities from the local store to
the cloud. This ensures that a fresh installation, or a machine that was offline
during a previous session, fully reconciles its local state before accepting new
writes.

The outbox pattern was chosen over alternative synchronisation strategies ---
such as two-phase commit or distributed transactions --- because it provides
eventual consistency without requiring the cloud database to be available at
write time, which is the defining constraint of the offline-operations
requirement (FR-09). The trade-off is that synchronised state may lag behind
local state during offline periods, but this is acceptable in a
personal-task-management domain where concurrent cross-device edits to the
same entity are expected to be rare.

\subsection{AI Integration}\label{sec:meth_ai}

The AI assistant communicates with a third-party large-language-model API.
Three operational modes are supported, each targeting a different model
variant optimised for general conversation, code generation, and document text
extraction, respectively. This design was chosen because no single model
variant excels at all three tasks --- code generation requires a model trained
on code corpora, while document extraction requires vision-language
capabilities.

The streaming delivery mechanism is a critical design consideration.
Rather than waiting for the full response to be generated on the server before
sending it to the client, the backend reads the API response incrementally and
forwards each token to the client as it arrives, using a server-sent events
(SSE) stream. This approach adds negligible latency between the model
producing a token and the frontend rendering it, providing a responsive typing
experience to the user. Alternative transports considered included long-polling
and WebSocket-based streaming, but SSE was chosen because it is natively
supported by browsers, requires no additional client libraries, and maps
naturally to the unidirectional server-to-client streaming pattern.

Conversation history is managed by loading a sliding window of recent messages
before constructing each API request, providing the model with sufficient
context while bounding the per-request token cost. After streaming completes,
the assistant's full response is assembled from all received fragments and
persisted as a new message. When a new conversation is started, the model is
asked to generate a short, descriptive title from the first user message, which
serves as the conversation's label in the sidebar.

\section{Frontend Design}\label{sec:meth_frontend}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Application Structure}\label{sec:meth_fe_structure}

The React application is organised as a flat module tree with client-side
navigation managed by a routing library. All application routes except those
related to authentication are protected by a guard component that redirects
unauthenticated users to the login page. Styling is managed entirely through
utility-first CSS classes, eliminating custom stylesheets and ensuring visual
consistency through a shared design token system. Third-party component
primitives are used for accessible interactive elements such as dropdown menus.

The build pipeline transpiles TypeScript sources and processes CSS through a
PostCSS pipeline, producing optimised bundles served by the backend's
static-file middleware.

\subsection{Task Visualisation Views}\label{sec:meth_views}

All five task views consume the same data from a shared state and differ only
in their rendering and interaction model. This design avoids duplicating data
fetching and transformation logic across views and ensures that a change made
in one view is immediately reflected in all others.

\textbf{Default View.}
Tasks are partitioned into temporal groups --- overdue, due today, due this
week, due later, and completed --- that replicate the mental model of a physical
in-tray sorted by urgency. Each group is rendered as a collapsible section.

\textbf{Kanban View.}
Tasks are arranged in columns corresponding to their status, with each column
header colour-coded to convey urgency. Tasks can be moved between columns via
drag-and-drop, which triggers an update request to the backend.

\textbf{Table View.}
Tasks are displayed in a columnar grid with sortable columns. Status and
priority are rendered as colour-coded badges. An expand toggle reveals a
sub-task scaffold row for future functionality.

\textbf{Gantt View.}
A full-calendar-year timeline renders each task as a bar positioned and sized
according to its due date, with colour coding for priority. The current date is
highlighted with a vertical marker, enabling at-a-glance workload assessment
over a long time horizon.

\textbf{Calendar View.}
A weekly time-grid displays tasks and calendar events as positioned blocks.
Tasks without a specific time are shown as all-day entries. A miniature
calendar sidebar allows week navigation.

Providing five distinct visualisations of the same data was a deliberate design
decision to support different user workflows and preferences --- some users
prefer a list sorted by urgency, others a spatial Kanban layout, and others a
temporal Gantt or calendar view --- without fragmenting the data model.

\subsection{Offline-Aware User Interface}\label{sec:meth_connbar}

A persistent banner at the top of the application layout communicates the
synchronisation state to the user. It subscribes to real-time connectivity and
sync-progress events from the backend, displaying:
\begin{itemize}
    \item An amber warning with a pending-operation count when offline;
    \item A blue progress bar advancing as outbox entries are processed
          during a synchronisation pass;
    \item Nothing when connectivity is healthy and no sync is in progress.
\end{itemize}
A manual-offline toggle is provided to allow users --- and, during development,
testers --- to simulate offline conditions without physically disconnecting
the network.

\subsection{AI Chatbot Interface}\label{sec:meth_chatbot}

The chatbot component provides a conversational interface to the AI assistant.
Toggle buttons at the top of the panel select the active mode, which
determines which model variant the backend queries. When no conversation is
active, a grid of starter prompts suggests questions appropriate for each mode,
helping new users understand the assistant's capabilities.

Messages are submitted through a form that supports both text input and file
attachment. The component opens a streaming connection to the backend for each
new message and appends incoming token chunks to the current message bubble as
they arrive, providing a real-time typing effect. When the stream closes, the
final assembled message is rendered with Markdown formatting and syntax-highlighted
code blocks.

A collapsible sidebar lists all saved conversations, sorted by recency, with
AI-generated titles and relative timestamps. Clicking a conversation loads its
full message history from the backend.

\section{Desktop Packaging}\label{sec:meth_desktop}
% ─────────────────────────────────────────────────────────────────────────────

The production build of TaskFlow is a self-contained desktop installer that
bundles three components: the native shell, the compiled backend, and the
frontend assets.

\subsection{Native Shell}

The desktop shell is built with a framework that uses the operating system's
native webview rather than bundling a browser engine. This approach was chosen
over alternative desktop-application frameworks --- such as Electron, which
bundles a full Chromium instance --- because it reduces the application's
distribution size by approximately 150~MB and its runtime memory footprint by
several hundred megabytes, while still providing access to native OS
capabilities through a plugin architecture.

The Rust source code is organised into three modules: plugin registration and
application setup, spawned-child-process management, and inter-process
communication commands accessible from the frontend.

\subsection{Sidecar Backend Management}

The backend is declared as a managed child process. On startup, the native
shell sets environment variables for the backend's runtime configuration and
launches the process. The backend announces its dynamically assigned port by
printing a well-known string to standard output. The shell parses this output,
stores the address in shared state, and signals the frontend.

The communication between the shell and the frontend is handled through
inter-process command invocations. These commands expose backend metadata
(dynamically assigned port, startup phase, application version, platform-
specific data directory), bridge the password-reset flow to the filesystem
context, and implement a custom window title-bar with native window controls
(minimise, maximise, close).

\subsection{Window Lifecycle}

Two windows are declared: a small, undecorated splashscreen shown while the
backend starts, and the main application window. Both start invisible. The
splashscreen is displayed during backend startup; when the backend signals
readiness, the main window is revealed and the splashscreen is closed. This
design prevents the user from interacting with a non-functional UI.

\subsection{Plugin Architecture}

A set of plugins provide the bridge between the web frontend and native OS
capabilities: process management for the sidecar lifecycle, single-instance
enforcement to prevent duplicate application processes, filesystem access for
password-reset codes and the application data directory, native file dialogs,
and HTTP access reserved for future use.

\subsection{Security Configuration}

The shell's security model is centred on a Content Security Policy that
restricts network connections to the local backend address and its WebSocket
endpoint, while allowing external font resources. A declarative capabilities
system grants granular permissions to individual plugins --- for example,
read access to specific files for password recovery and the ability to open
URLs in the system browser. The security configuration allows the application
to comply with the principle of least privilege: only the minimum set of
capabilities needed by each feature is granted.

\subsection{Build Pipeline}

The production build is orchestrated by a script that executes a sequential
pipeline: deterministic dependency installation, TypeScript type checking,
frontend asset bundling, self-contained backend compilation targeting the
current platform, staging of the compiled backend as a sidecar binary, and
final shell build producing an installer. The resulting installer is
self-contained: no .NET runtime, Node.js, or Rust toolchain is required on
the target machine.

The webview runtime is handled by the installer configuration, which downloads
and installs it only if it is not already present on the system. On modern
versions of Windows, the webview is integrated into the operating system, so
this step is typically skipped.

\section{Testing Strategy}\label{sec:meth_testing}
% ─────────────────────────────────────────────────────────────────────────────

Testing was conducted at three levels throughout the development process.

\textbf{Unit-level verification.}
Service-layer logic was verified by constructing services with an in-memory
database provider and asserting expected state after each operation.
Authentication middleware resolution and credential hash round-trips were tested
in isolation.

\textbf{API integration testing.}
Each controller was exercised against a running server instance. The tests
verified: (a) that the authentication middleware resolves the user correctly
in all cases; (b) that ownership checks return appropriate error codes for
resources belonging to a different user; and (c) that create, read, update, and
delete operations produce the expected HTTP status codes and response bodies.

\textbf{Offline synchronisation testing.}
The synchronisation pipeline was validated by toggling the application into
manual-offline mode, performing a series of operations, confirming that outbox
entries were created, then toggling back online and observing the replay
process complete successfully.

\textbf{Desktop packaging.}
The installer was tested on multiple versions of Windows. In all cases the
application launched, authenticated, and performed offline task creation and
synchronisation without errors.
